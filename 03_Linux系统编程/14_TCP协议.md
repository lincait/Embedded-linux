# TCP 协议

TCP（传输控制协议）是一种**面向连接的、可靠的、基于字节流**的传输层协议，用于**给应用层提供端到端的可靠传输**。在发送数据之前，通信双方必须先建立连接，之后通过序列号、确认应答、重传、流量控制和拥塞控制等一系列机制保证数据可靠到达。

# TCP 的特征

- **面向连接**：数据交换前先通过三次握手建立连接，确保双方都准备好。
- **可靠传输**：发送方为每个报文段分配序列号，接收方回 ACK 确认；超时未确认则重传。
- **流量控制**：用窗口大小机制防止发送方太快，导致接收方缓冲区溢出。
- **拥塞控制**：用慢启动、拥塞避免、快速重传、快速恢复等算法，避免网络过度拥塞。
- **数据排序**：报文段可能乱序到达，TCP 根据序列号重排，保证按序交付应用层。
- **端到端通信**：一个 TCP 连接由四元组唯一确定：源 IP、源端口、目标 IP、目标端口。

# TCP 报文段格式

TCP 头部比 UDP 复杂得多，关键字段如下：

- **源端口 / 目标端口**：各 16 位，标识通信的应用程序，让操作系统区分不同网络服务。
- **序列号（seq）**：32 位。TCP 把数据看成无结构的字节流，不是对报文段中的每个比特进行编号，而是对**应用数据字节流**中的每一个字节进行编号。一个报文段的序号是它**首字节**在字节流中的编号。序号是虚拟的逻辑编号，是为了在不可靠的 IP 网络上实现可靠传输而设计的一种机制。
- **确认号（ack）**：32 位。当 ACK 标志为 1 时，表示发送方**期望从对方收到的下一字节的序号**，即对之前数据的确认。一个报文段的确认号是对方发送来的序列号加上数据长度，但如果该报文段包含 SYN 或 FIN，还需额外加 1，也就是说只有数据、SYN和FIN才会占用序号。发回去是就是告诉对方下次从这个确认号开始传输。
- **数据偏移**：4位
- **保留位**：6位
- **控制位**：6 个标志位，每个 1 比特：
  - `URG`：有紧急数据，接收方应优先处理。
  - `ACK`：确认号有效。连接建立后所有报文段 ACK 都为 1。
  - `PSH`：接收方应立即把数据交给上层。
  - `RST`：连接出错，要求终止并重新建立连接。
  - `SYN`：建立连接时使用，前两次握手为 1。
  - `FIN`：发送方没有数据要发了，想断开连接。
- **窗口大小**：16 位，告诉对方自己还能接收多少数据，用于流量控制。
- **校验和**：16 位，检查整个报文段的完整性。
- **紧急指针数据偏移量**：16位，用于校验

# TCP 连接的建立：三次握手

- 服务端：等待连接的。
- 客户端：主动建立连接的。

建立连接前，服务器先调用 `listen` 进入 LISTEN 状态（**被动打开**），客户端发起连接（**主动打开**）。用 `seq` 表示序号、`ack` 表示确认号，未提到的标志位均为 0：

1. **第一次握手**：客户端发送 `SYN=1, seq=ISN(c)`（随机初始序号）的报文段，请求建立连接，进入 SYN-SENT 状态。
2. **第二次握手**：服务端收到后进入 SYN-RCVD 状态，回复 `SYN=1, ACK=1, ack=ISN(c)+1, seq=ISN(s)`（服务端自己的随机序号）。
3. **第三次握手**：客户端收到后进入 ESTABLISHED 状态，回复 `ACK=1, ack=ISN(s)+1, seq=ISN(c)+1`。服务端收到后也进入 ESTABLISHED 状态。

# TCP 连接的释放：四次挥手

挥手可以由任一方发起，这里假设客户端主动断开（主动关闭），断开前双方都处于 ESTABLISHED 状态：

1. **第一次挥手**：客户端发送 `FIN=1, ACK=1, seq=U, ack=V`，表示不再发送数据，进入 FIN-WAIT-1 状态。
2. **第二次挥手**：服务端回复 `ACK=1, ack=U+1, seq=V`，进入 CLOSE-WAIT 状态；客户端收到后进入 FIN-WAIT-2 状态。此时服务端**还可以继续发数据**，客户端仍能接收。
3. **第三次挥手**：服务端把剩余数据发完后，发送 `FIN=1, ACK=1, ack=U+1, seq=W`，进入 LAST-ACK 状态（被动关闭）。
4. **第四次挥手**：客户端回复 `ACK=1, ack=W+1, seq=U+1`，进入 TIME-WAIT 状态；服务端收到后进入 CLOSED。

客户端在 TIME-WAIT 状态要等 **2 倍 MSL**（最大报文生存时间）才关闭。原因：确保最后一个 ACK 能到达服务端——如果丢了，服务端会重发 FIN，客户端还能再回应；同时让旧的重复报文在网络中自然消亡，不会干扰新连接。

> 为什么挥手要四次而握手只有三次？握手时服务端的 SYN 和 ACK 可以合在一个报文段里发（反正还没开始传数据）；挥手时服务端收到 FIN 后可能还有数据要发，不能立刻回 FIN，只能先回 ACK 确认，等数据发完再单独发 FIN，所以多了一次。

## 相关的关键状态

- `LISTEN`：服务器等待连接请求。
- `SYN-SENT` / `SYN-RCVD`：握手过程中的中间状态。
- `ESTABLISHED`：连接建立，正常传输数据。
- `FIN-WAIT-1/2`、`CLOSE-WAIT`、`LAST-ACK`、`TIME-WAIT`：挥手过程中的状态。
- `CLOSED`：初始和最终状态。

可以用 `netstat -tnp` 或 `ss -tn` 查看当前 TCP 连接的状态。

# 可靠传输机制

- **累积确认**：接收方 ACK 中的确认号表示"期望收到的下一字节序号"，意味着所有小于它的字节都已成功接收。
- **延时确认**：接收方收到报文段后不立即回 ACK，稍等片刻看是否有其他报文段到达，把多个确认合并成一个 ACK 发送，减少网络开销。
- **超时重传**：发送方在限定时间内没收到 ACK，就认为报文段丢失，重新发送。

# 滑动窗口：流量控制

双方各自维护一个缓冲区。如果发送速率大于接收速率，接收方缓冲区会被填满，后面到达的数据只能被丢弃。TCP 在报文段头部的**窗口大小**字段中携带**接收窗口（rwnd）**——告诉发送方自己当前还有多少可用缓冲区。接收窗口随数据处理动态变化，变成 0 时发送方暂停发送，接收方腾出空间后再通知它继续。

滑动窗口机制确保发送的数据不会超出接收方的处理能力，这就是**流量控制**。

# 拥塞控制

接收窗口只能防止接收方处理不过来，但网络本身也可能拥堵。设想 rwnd 允许发 10 个报文段，而网络极限只能承受 5 个，发出去必然拥堵丢包，发送方超时重传，进一步加剧拥堵，恶性循环。

为此 TCP 维护**拥塞窗口（cwnd）**，是发送方根据网络状况自己算出来的：

- **慢启动**：连接建立后 cwnd 从 1 开始，每收到一个 ACK 翻倍（指数增长）。
- **拥塞避免**：cwnd 达到慢启动阈值 ssthresh 后，每收到一个 ACK 只加 1（线性增长）。
- **超时重传**：检测到超时，把 ssthresh 减半（当前cwnd的一半），cwnd 重置为 1，重新慢启动。
- **快速重传**：连续收到 3 个重复 ACK 就判定报文段丢失，不等超时立即重传。
- **快速恢复**：快速重传发生时，ssthresh 减半，但 cwnd 不从 1 开始，而是直接等于新 ssthresh，进入拥塞避免。

最后，接收窗口管"接收方扛不扛得住"，拥塞窗口管"网络扛不扛得住"，所以真正决定发送量的是**发送窗口 swnd = min(rwnd, cwnd)**。
